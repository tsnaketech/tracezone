# Security Policy

TraceZone is a read-only lookup tool. It has no accounts, no database, no cookies
and no session state, so most classes of web vulnerability do not apply to it.
The parts that _do_ matter are the outbound requests it makes to registries and
the way user input reaches them — those are documented below.

## Reporting a vulnerability

Please report privately through
**[GitHub Security Advisories](https://github.com/tsnaketech/tracezone/security/advisories/new)**
rather than opening a public issue.

Please include:

- what you did (a `curl` command or a URL is ideal);
- what happened, and what you expected;
- why you think it is a security issue rather than a bug.

You should get an acknowledgement within a few days. This is a side project with
no on-call rotation, so please do not expect an SLA. Fixes land on `main` and
deploy automatically; you will be credited in the advisory unless you ask not to
be.

Please do not run load tests, scanners or brute-force tooling against the hosted
instance — the rate limiting is best-effort (see below) and the upstream requests
it triggers hit third-party registries, not us. Run the app locally instead:

```bash
pnpm install && pnpm dev
```

## Supported versions

There is a single supported version: the current `main` branch, which is what is
deployed. There are no releases, tags or backports. Fixes are not backported to
older commits.

## What is in scope

- The hosted application and its API.
- Anything in this repository.

Findings likely to be considered valid: bypassing the outbound request
restrictions below, getting TraceZone to fetch an address it should refuse,
injecting content into a rendered page, or causing an unhandled crash that leaks
internal detail.

## What is out of scope

- **Rate limiting is best-effort and known to be weak.** The counter lives in
  each serverless instance and edge-cached responses never reach it, so the
  effective limit does not converge. This is documented in
  `src/lib/api/rate-limit.ts` and in the API docs. Reports that the limit can be
  exceeded are not vulnerabilities — they are the documented behaviour. A shared
  store is the known fix.
- **Missing headers reported by a scanner without an exploit path.** The header
  set is deliberate; see below.
- Denial of service through sheer volume, and anything requiring physical or
  local access to a user's device.
- Vulnerabilities in upstream RDAP registries. Report those to the registry.
- The content of RDAP responses. TraceZone displays what registries publish,
  including redacted placeholders; it never attempts to unmask them.

## Security design

These are the properties worth attacking, and where they are implemented.

### No user-supplied URL is ever fetched

There is deliberately no endpoint of the form `/api/proxy?url=…`. RDAP URLs are
built in `src/lib/rdap/client.ts` from a constant base — discovered through the
IANA bootstrap registry, or the `rdap.org` redirector — plus a single
URL-encoded path segment. A caller can influence _which domain_ is looked up,
never _which host_ is contacted.

### Outbound request restrictions

Every outbound request goes through `src/lib/net/safe-fetch.ts`, which enforces:

- HTTPS only, on the default port;
- no credentials in the URL;
- no IP literals, loopback, link-local or non-public hostnames (SSRF);
- redirects followed manually, re-validated at **every** hop, capped at 3;
- a wall-clock timeout;
- a hard cap of 2 MB on any buffered response body.

### Time budget

A lookup may query several candidate names, so the whole operation shares one
8 s deadline (`src/lib/net/deadline.ts`); a single RDAP request gets 5 s or
whatever the deadline has left, whichever is smaller. The deadline sits below the
10 s serverless function limit so the lookup always fails on its own terms.

### Input validation

Domain names are validated and normalised in `src/lib/validation/domain.ts`
before anything else happens. Input that cannot be resolved unambiguously is
rejected rather than guessed. Query parameters are parsed strictly: an
unrecognised value is an error, not a silent fallback.

### Response headers

The Content-Security-Policy is generated by Astro with per-page hashes for its
own inline scripts and scoped styles, so `script-src` carries no
`'unsafe-inline'`. The remaining directives are declared in `astro.config.mjs`.

`X-Content-Type-Options`, `X-Frame-Options`, `Referrer-Policy`,
`Permissions-Policy`, `Strict-Transport-Security` and `Cross-Origin-Opener-Policy`
are set in `src/middleware.ts` for on-demand responses and in `vercel.json` for
the static layer. `frame-ancestors` cannot be expressed in a meta-tag policy,
which is why framing is denied with `X-Frame-Options` instead.

### CORS

The API sends `Access-Control-Allow-Origin: *`. It is public, unauthenticated
and read-only, and nothing depends on cookies or credentials — there is no
ambient authority for a third-party page to borrow.

### Data handling

- No database, no analytics, no third-party scripts, no web fonts.
- Client IP addresses are used only as an in-memory rate-limit key for the
  duration of one window. They are never logged or persisted.
- Errors never carry a stack trace or internal detail; every unexpected
  throwable collapses to a generic `INTERNAL_ERROR` (`src/lib/api/errors.ts`).
- Lookup queries are not stored. They do reach the upstream registry, which has
  its own logging and privacy practices.

### Secrets

The application requires no secrets and no environment variables. The single
optional variable, `PUBLIC_SITE_URL`, sets the canonical origin at build time and
is public by definition. Anything imported by a hydrated Svelte island can reach
the browser, so `src/lib/config.ts` holds public constants only.

## Dependencies

Runtime dependencies are deliberately few: Astro, Svelte, Tailwind and
`@toon-format/toon`. Domain validation and punycode conversion use the platform's
own `URL` parser rather than a dependency. CI runs `pnpm install --frozen-lockfile`
so a build cannot silently pick up a different tree than the lockfile describes.
